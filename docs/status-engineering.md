The developer-facing companion to [limitations.md](limitations.md): the same list, with the dates,
counts, rule names and research pointers that back each status. If you want to know WHETHER
something works, read limitations.md; if you want to know HOW WE KNOW, read this. Ordered the way a
player hits things: connecting, moving, fighting, talking, managing the
party, shops/minigames, more than two players, input, then a list of things that look like bugs on
the rig but aren't real limitations. Sources: `docs/roadmap-seamless.md` (roadmap row numbers
below), `docs/live-verification.md`, `README.md`, and the `docs/research/` write-ups named inline.

Status words used below: **Works** (live-verified on the two-instance rig), **Partial** (works
with a real, stated gap), **Not supported** (missing or refused by design), **Unverified**
(built and unit-tested, never watched on the running game — 🎮 NEEDS-LIVE in the roadmap).

**The v0.9.0 sidecar bug (fixed 2026-09-03, after the tag).** World adoption stages the host's
save — host PC and all — into `saves\000001 - AUTOSAVE`, and `SaveDigest.FindSessionSave`
prefers that slot because it IS the save the session is playing. The "resume tomorrow" capture
(`SessionSaveWatch`, on a save edge and on every clean disconnect) used the same lookup, so
every disconnect lifted the HOST's player out of the staged copy and wrote it over the joiner's
sidecar; on the next join `ShouldPreferSidecar` saw a sidecar newer than the joiner's own save
and carried the host's character in. Caught on the first `join_mode = auto` live pass (the
`session-saved character: carried the character from '000001 - AUTOSAVE' ... (11918 bytes)` line
fired one second before the adoption, and the pifo then contained the host's name). The fix is
`StagedSave`: adoption records the staged `SAVEGAME.sav` (size + mtime) in
`saves\kotorcoop-staged.json`, captures read `ClientCharacterPersistence.FindCaptureSource`
(this install's newest save, skipping the staged copy) and refuse a source older than the
sidecar; with no marker at all (an install upgraded mid-life) the autosave slot's own content
decides — the engine writes a live `pifo` into every autosave it makes, a staged world carries a
renamed one or none. All three live-verified 2026-09-03: marker match → `kept the sidecar`,
marker deleted → still kept (content rule), client quicksave → disconnect → sidecar rewritten with
the joiner's own PC. Anyone who joined on v0.9.0 with `join_mode = save` and quit at least once
may have a corrupt sidecar; the next `join_mode = auto` join (the new default) carries whatever
the sidecar holds, so delete `saves\kotorcoop-character.*` once after upgrading if the joiner
comes up as the host's character.

## Known rig-only artifacts (not real limitations)

These showed up during live testing and are worth knowing about if you're chasing a "bug" — they
are testing-rig quirks, not things a real playthrough will hit:

- **Console `god on` on the client PC** trips the absorb watchdog during combat traces — a testing
  artifact of the dev cheat, not a co-op defect (live-verification.md, N-slot round).
- **A stale plugin build in a second/third game directory** produced a false "nothing happening on
  the client" reading in two separate rounds (3+ peers, swoop) — always compare installed DLL
  sizes before trusting a negative result.
- **The `movenear`/`movenear <id>` console verb** resolves a stale id against Trask in `tar_m10aa`,
  snapping him to (0,0,0) — a dev-verb quirk, not a gameplay bug; move the host's PC instead.
- **A plugin log that suddenly goes quiet does NOT mean a stalled or dead plugin** (2026-09-16/17).
  A session was reported as "the host's plugin wrote nothing for the rest of the session after
  `topup`, and the client's walks stopped moving the phantom". Two reproduction attempts on
  2026-09-17 — soldiers spawned, the host attacking, both players on the Endar Spire's 1-hp floor,
  then `topup` — reproduced the silence (60 s+, zero lines) and NOT the fault: the console still
  answered (`status`, reply serial advancing) and the client's walks still drove the phantom on the
  host's screen (18 → 21 → 25 in `creatures.ps1`). The only per-second line at that moment is the
  `attack probe` diagnostic, and it closes its own window when the target dies — after that there
  was simply nothing due to log. The original three-hour silence was the ENGINE parking its main
  loop while the game window was inactive/the displays asleep; the same rig reproduced that gap
  exactly (host log 23:10:04 → 02:09:39, ending in `render window activated` the instant the window
  was hovered, followed by `party follow stall: 0x127 wedged 12273.1s` = the length of the sleep).
  The stall watchdog is now two-sided and closes its own bracket — the worker reports a frame hook
  quiet for >2 s *and* when it resumes with the measured duration, and the game thread reports the
  same for the worker — so this question is a grep, not a reproduction.
- **Screenshot/screen-capture tooling on the rig has been unreliable**, which is why the M-key map
  appearance is still marked Unverified even though its underlying data path is confirmed working.
  The connection indicator's own render/collision-avoidance was confirmed a different way
  (`tools/textqueue.ps1`, 2026-09-10) without needing a screenshot — only its exact pixel position
  at other resolutions remains open.

## Appendix B — detailed limitation notes (moved from README.md, 2026-09-03)

The long-form engineering notes that used to be README.md's "Honest limitations" bullets. Links are
relative to the repository root as they were there.

- **Only the host can switch party character**, mirrored to everyone else; control returns to your own character automatically on connect (`control_return=0` opts out). A mirrored companion's follow-AI never runs at all while mirroring holds, by design (the reclaim that keeps local AI from contesting a driven position also blocks the engine's own follow dispatcher). Where follow-AI DOES run, its long-standing "companion stands still and never catches up" stall is fixed and on by default (`party_follow_stall_recovery`, 2026-08-29): a runtime detector spots the exact wedged follow record and gathers the party through the engine's own routine, the same one a module transition uses — five reps, every wedge recovered on the first attempt. It relocates the companion rather than walking it back; the long-distance pathfinding limit underneath is real and still unfixed, so a companion left far behind is gathered, not walked. `disconnect` then `reconnect` reliably re-mirrors a companion. A mirrored companion can't fight for a client except through `companion_local_combat`, which **ships OFF by default** (a player sets `companion_local_combat = 1` in `coop.ini`); a companion it releases then forwards the damage it actually takes back to the host, which spends it as real damage on its own authoritative body (`companion_damage_sync`, on by default, NEEDS-LIVE) — before this, a released companion's damage went nowhere and the host's own mirror write overwrote it on the very next pass, making it effectively invulnerable. See [control-return.md](research/control-return.md), [party-reconciliation.md](research/party-reconciliation.md) and [companion-state-sync.md](research/companion-state-sync.md) §13.
- **One conversation at a time**, by design — the other player spectates rather than a separate copy; any peer may start one (initiator-led replies), and (2026-08-29) a spectator's SKIP is swallowed the same way clicks already were (`DialogueSkipHook`). See [dialogue-sync.md](research/dialogue-sync.md).
- **Losing the host doesn't lock you out, live-verified.** A client whose host crashes, quits, or drops off the network releases every co-op lock within `host_loss_timeout_ms` (default 5000ms — measured live at 6.1s) and keeps playing solo — companions, doors and dialogue all keep working — while re-Helloing automatically in the background; the host coming back re-mirrors everything with no player action needed (`host_loss_release`, on by default, `PacketType.HostBye` fast path). See [disconnect-reconnect.md §11](research/disconnect-reconnect.md).
- **Companion experience and equipment sync are both live-verified and on by default** (`companion_xp_sync`, `companion_gear_sync` — see the status table); **dialogue recruitment sync is live-confirmed for two companions** and **ships ON by default since 2026-09-18** (it was OFF in code before that, and `profiles/coop.ini.example` no longer carries the key; with it off a companion recruited on one instance is never made available on the other — see `PartyRosterController`'s own doc comment). A fix for a stale pre-recruit body isn't yet confirmed live either way. See [companion-state-sync.md](research/companion-state-sync.md), [dialogue-consequences.md](research/dialogue-consequences.md).
- **Mod-compatibility mismatch handling is live-verified for most categories**, but module-GIT/globals-catalogue mismatches are unforced in testing and a same-resref, differently-modded item isn't detected. See [mod-compatibility.md](research/mod-compatibility.md).
- **Swoop racing works, but only one player at a time.** The "the race never starts" report turned out to be a wrong test recipe, not the mod: the race branch of Gadon's dialogue needs the `Tar_SummonGadon` global and three real reply picks, and with those it runs end to end. A KOTOR track is a single-seat area, so `minigame_lock_peers` (on by default, `minigame_lock_timeout_s=600`) holds the other players still with a "&lt;name&gt; is racing - waiting" notice and refuses to warp them onto the track; rewards (gold, journal, the `Tar_Swoop*` globals) reach everyone through the ordinary channels. The keyboard half of that peer lock stays NEEDS-LIVE (injected keystrokes never reach this game); the `delay_probe` diagnostic ships OFF. **Creature liveness reconciliation** (a body alive on one screen, dead on the other) ships ON by default since 2026-09-03 — destroy/kill dispatch and a 49-creature freshness probe all verified live; the one known cosmetic is up to ~1.5 s of budgeted `liveness ANOMALY` log lines on a client right after a kill on the host's authority, before the census drops the id. See [minigames.md](research/minigames.md) §24 and [creature-liveness.md](research/creature-liveness.md).
- **A peer could be INVISIBLE to a joining player for a whole session — closed 2026-09-17.** The body was spawned in the gap between the server world coming up and the client world being built; it then tracked its peer perfectly and was never drawn. Nothing readable from memory distinguishes such a body from a working one, so the gate is on the LOCAL player having a rendered body before any phantom is spawned. See [name-plates.md](research/name-plates.md) "The invisible peer".
- **A peer could render as the wrong character (a stranger, or Trask) after a warp — both root causes closed, 2026-08-29.** The phantom's client twin is now re-dressed after re-spawn (`PeerIdentityRule`), and a host companion no longer leaks into the enemy census during the ~5s its follow pointer is null after a transition (`PartyCensusRule`, roster-based) — stand-ins built for a genuine enemy are dressed too. See [name-plates.md](research/name-plates.md) and [TROUBLESHOOTING.md](TROUBLESHOOTING.md).
- **Chain mode serialises `dinput8` proxies, it doesn't merge them** — a proxy that always loads the system DLL itself must be last in `dinput8.chain`; "load me" DLLs (`.asi`) go anywhere.
- **Each player really fights up to 3 enemies at a time (`local_combat_slots`, default 3, live-verified 2026-09-02).** `local_combat` hands a client up to `local_combat_slots` hostiles to its own engine at once (1 reproduces the original single-fight behaviour); every other engaged enemy beyond that count stays mirrored (damage still lands), and the damage wire names only the last attacker. Built and unit-tested 2026-09-02; two Sith on one client at once with two cross-side kills confirmed live the same night (live-verification.md 2026-09-02, "N-slot round"). See [combat-participation.md §11](research/combat-participation.md).
- **An enemy shares its attention between both players, but does not stay pulled.** `threat_retarget` (ON by default since 2026-09-03) orders an enemy the host engaged first onto the client once the client's forwarded damage clearly leads; the order lands every time, but KOTOR's own AI re-picks the host PC on its next landed hit, so in a shared fight the enemy alternates (measured 12 hits on the host's PC vs 10 on the client's phantom over 98 s — 0 on the client without it). Only tracks the ONE remote peer's damage — with 3+ players it is inert. See [peer-damage-ledger.md §11](research/peer-damage-ledger.md).
- **The party's shared item pool and merchant store stock are synced, at mode 2** (`party_pool_sync`/`store_sync`, both ON by default since 2026-08-29 — see the status table). Two live-verified limitations remain: a shop's stock can only be READ while some player has that shop's GUI open (an engine limitation, unchanged from mode 1), and an infinite-stock item's buys never replicate because the engine's own stock never changes for one. Mode 1's bidirectional op-log stays disqualified and is reachable only by writing `=1` explicitly. See [party-pool-sync.md](research/party-pool-sync.md), [store-sync.md](research/store-sync.md) and [shared-inventory-v2.md](research/shared-inventory-v2.md).
- **The Star Forge's Bastila and Malak duels spectate, ON by default and live-verified** (`solo_segment_spectate`), except the input lock is only confirmed to engage its own mechanism, never confirmed to stop a real PHYSICAL WASD press (injected keystrokes never reach this game — same limit as the swoop peer lock above).
- **Chaining the console `warp` verb rapidly can crash the game** — a pre-existing, unfixed `swkotor.exe` defect, not co-op-specific and not gated by any `coop.ini` setting. A 12-transition real-doors-only soak found zero crashes on the same build a `warp`-driven soak crashed by transition 2-3 on. See [transition-crashes.md](research/transition-crashes.md) and [docs/CONSOLE.md](CONSOLE.md)'s `warp` row.
- **A real door crossing used to cost the client a needless rejoin — fixed 2026-09-03.** The engine autosaves through every module transition, and each side's autosave carries its own runtime-id counters, so the two "save identities" disagreed for good after the first door and the client auto-rejoined mid-cutscene (`W_SAVE`). A save-identity mismatch is now honoured only when the two sides never agreed or one of them has loaded a save since; a mismatch that can only have come from a save is the same world. See [session-save.md](research/session-save.md) and [cinematics.md](research/cinematics.md) §8.3c.
- **`coop.ini` divergence is negotiated, not silent.** Every behaviour flag rides a digest compared at join; a difference always warns on both screens (`W_CFG`), and nine host-authoritative keys are additionally adopted by a disagreeing client at runtime. See [mod-compatibility.md](research/mod-compatibility.md)'s "Behaviour-flag negotiation".
- **The other player's movement should look continuous, not bursty.** Until 2026-08-29 it did not: the agent's item cache was forcing a full ~180 MiB scan of the game's memory once a second on the same thread that writes remote players' positions, so the pump ran at 12.8 Hz instead of 30 with individual ticks up to 2.4 seconds. Every world scan now runs on a background thread and serves its previous result while refreshing; measured on the rig, the worst tick went from 2,409 ms to 8.4 ms and the pump holds 30 Hz. If a peer still moves in bursts, that is a bug worth reporting — turn on `perf_trace` and send the agent log. See [lag-audit.md](research/lag-audit.md).
- **The Endar Spire's command deck floors damage at 1 hp for everyone** — KOTOR's own tutorial script, not this mod ([min-one-hitpoint.md](research/min-one-hitpoint.md)).
- **A controller can play but not type.** `DirectInputKeyboardHook` wraps the game's own keyboard device and appends pad-derived DIK events to its buffered read; the cursor and clicks are posted window messages. Edit boxes (address/password, chat, console) take `WM_CHAR` text the pad has no way to produce — see [gamepad.md](research/gamepad.md).
- **Internet play works without a relay for most home routers, not all.** A host's public address is found automatically (STUN) and the port forwarded via UPnP (manual otherwise, named in `status`/`public_address`); no relay/hole-punching, so a restrictive ("symmetric") NAT with UPnP off can't be reached, and a host behind carrier-grade NAT can't be reached by any mapping — which the status line now detects and says (2026-09-18 self-probe, [network-topology.md §17](research/network-topology.md)). The one real-router attempt (2026-09-10) failed exactly that way. See [network-topology.md](research/network-topology.md).
